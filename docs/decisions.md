## 1. Что есть сейчас (исходная точка)

Рабочий скрипт развертки 1С-проектов (PowerShell 5.1, автономный, **без прав администратора**):

```
C:\1C_Bases\AI\1c-deploy_new\deploy-new-1c-project-ru-publish.ps1
```

Что делает один прогон (`.dt` → готовый проект для AI-разработки):

1. **Параметры** (CLI или интерактивный ввод): TemplateDir, ProjectDir, DtPath, PlatformPath,
   IbcmdPath, DbUser/DbPassword, Prefix (по умолч. `ФК_`), NewObjectsIn (`extension`),
   ApacheDir (portable Apache 2.4), PublishPort (по умолч. 8080), RulesSource/RulesCacheDir,
   SkipRulesUpdate, BslAnalyzerDir/Version, SkipBslAnalyzer, JavaPath,
   PlatformContextDir/Version, SkipPlatformContext.
2. Автодетект платформы в `C:\Program Files\1cv8\<версия>` (выбор из установленных) и `ibcmd.exe`.
3. Создание папки проекта, копирование эталона: `env.json`, `packagedef`, `.kilo/kilo.json(.jsonc/.gitignore)`, `tools/mcp-1c` (mcp-1c.exe + MCP_HTTPService.cfe).
4. Патч `.dev.env` (PLATFORM_PATH/VERSION, INFOBASE_PATH=build\ib, INFOBASE_KIND=file, IB_USER/PASSWORD, EXPORT_PATH=src\cf, EXTENSIONS_PATH=src\cfe, PREFIX, NEW_OBJECTS_IN) и `env.json` (профиль default: --ibconnection `/F"...""`, --db-user, --db-pwd, --v8version, --root, --workspace).
5. Создание структуры каталогов проекта (.1cpt, build, docs, src\epf, tests, tools, vendor и др.).
6. **Создание ИБ из .dt**: `ibcmd infobase create --db-path=<ib> --create-database --restore=<dt>`.
7. **Проверка блокировок ИБ**: ненулевые `*.1cl`, зависшие 1cv8/1cv8c/designer с этой ИБ, ibsrv с `--db-path=<ib>`; цикл «исправил — проверь ещё раз» (сейчас интерактивный).
8. **Установка расширения MCP_HTTPService**: `mcp-1c.exe -install <ib> -platform <1cv8.exe>` (через Конфигуратор, декларирует MCP_ОсновнаяРоль), затем `ibcmd config extension update --safe-mode=no --unsafe-action-protection=no`.
9. **Дамп основной конфигурации**: `ibcmd infobase config export` → `src/cf`.
10. **Дамп расширений**: `ibcmd config export all-extensions` → `src/cfe`.
11. **Веб-публикация в portable Apache** (без службы, без админа, порт >1024):
    патч `httpd.conf` (SRVROOT, Listen, ServerName, LoadModule wsap24 + Include, маркерный блок),
    блок публикации в `conf/1c-publications.conf` (маркеры `# project: <id>` / `# end project: <id>`,
    один Apache обслуживает много баз), `build/publish/default.vrd`
    (File=..., опц. Usr/Pwd внутри строки ib, httpServices publishByDefault + publishExtensionsByDefault, ws enable),
    рестарт httpd.exe (свой видимый консольный процесс), probe `GET /<vdir>/hs/mcp-1c/version`,
    запись INFOBASE_PUBLISH_URL в `.dev.env`. Веб-клиент: `http://localhost:<port>/<vdir>/ru_RU/`.
12. **Правила AI-агента**: кэш-клон ai_rules_1c (git clone/fetch+reset), `install.ps1 -Command init -ProjectRoot <dir> -Tools kilocode -NonInteractive -AssumeYes`.
13. **bsl-analyzer**: установка официальным install.ps1 в %LOCALAPPDATA%\Programs (без админа), `bsl-analyzer.toml` (root=src/cf), MCP-записи workspace/reference в `.kilo/kilo.json`, управляемый блок в `USER-RULES.md`.
14. **mcp-bsl-platform-context**: java 17+ (проверка версии), fat-JAR с GitHub Releases (кэш в tools, переиспользуется между проектами), MCP-запись `bsl-platform-context` (--platform-path), блок в USER-RULES.md.
15. **kilo.json**: `1c-data-mcp` переводится на локальный stdio-прокси (`tools/mcp-1c/mcp-1c.exe -base <publishUrl>/hs/mcp-1c [--dump src/cf]`); все прочие MCP-серверы каталога отключаются (enabled=false, whitelist-режим).
16. Итоговый лог `fk_deploy_log.bsl`, открытие в VS Code.

Важные свойства текущего скрипта (сохранить при рефакторинге):
- **Полная идемпотентность** шагов (маркерные блоки в httpd.conf / 1c-publications.conf / USER-RULES.md / kilo.json, пропуск уже выполненного).
- Прогресс длинных операций 1cv8/ibcmd через хвост лога дизайнера («Обрабатывается: <объект>», «Выгрузка …»).
- Аккуратная работа с PS 5.1: UTF-8 no BOM, экранирование аргументов Start-Process, $ProgressPreference при скачиваниях и т.п.
- Всё работает **без прав администратора**.

## 2. Цель проекта

Графический интерфейс — **«личный кабинет» в браузере** для управления развертками 1С:
- список/карточки развернутых проектов (статус, ссылки: веб-клиент, MCP, VS Code, логи);
- новая развертка рабочего пространства (все пункты скрипта) через визард;
- монитор прогона в реальном времени (шаги, живой лог, прогресс);
- управление публикациями (публикация/снятие/порт/рестарт Apache) для уже развернутых баз.

Заложить модульность под будущие функции:
1. развертка в **серверную** базу;
2. подключение **агента / MCP-серверов** к уже развернутым базам (файловым и серверным);
3. **индексация** проектов для лучшей работы AI-агента.

## 3. Жесткие ограничения

- **Без прав администратора** — весь стек.
- Windows, PowerShell **5.1** (код ядра должен работать на 5.1; не полагаться на pwsh 7).
- HTTP-порты **выше 1024**; кабинет слушает **только 127.0.0.1** (не спрашивать брандмауэр).
- Никаких системных служб и URL ACL (netsh http) — всё процессы пользователя.
- Portable Apache (`C:\1C_Bases\AI\tools\apache_portable\Apache24`) остается средством публикаций ИБ; кабинету он не нужен — у него свой порт.

## 4. Принятые архитектурные решения

### D1. Вариант интерфейса: локальный веб-кабинет (из сравнения с WPF / VS Code extension / Electron)
Бэкенд-процесс на localhost + страница в браузере. Полностью удовлетворяет «кабинету», живым логам и работе без админа.

### D2. Backend: PowerShell (ядро шагов) + HTTP-сервер на «сыром» TcpListener
- Ядро развертки **обязано** остаться на PowerShell — это обертки над ibcmd/1cv8/Конфигуратор/Apache, текущий код проверен годами.
- **Актуализация (2026-10-30):** вместо Pode — **собственный минимальный HTTP-сервер** на TcpListener
  (`backend/server.ps1`, тот же подход, что внутри Pode). Причины: Pode требует `Install-Module`
  на каждой машине, где запускается кабинет — противоречит требованию «скопировал папку — работает».
  Плюсы: ноль установок, кабинет переносим вместе с репозиторием. Ограничения: однопоточный
  (запросы обрабатываются последовательно — для локального одного пользователя достаточно),
  без SSE (живой лог пока через перечитывание файлов прогона; SSE вернем на этапе 0 при runner).
- Слушает только 127.0.0.1, порт 8180 (>1024). Рантайм: консольный процесс пользователя.
  Запуск одним кликом: **`start-cabinet.cmd`** в корне (стартует бэкенд и сам открывает
  кабинет в браузере на http://127.0.0.1:8180/; переключатель `-NoOpenBrowser` — не открывать).
- Альтернатива на вырост (не выбрана): ASP.NET Core Minimal API — потребует .NET runtime у коллеги.

### D2. Backend: Electron-приложение (актуализация 2026-10-30, вытеснила Pode/PS-сервер)
- **Текущий рантайм:** `electron/main.cjs` — main-процесс Electron. Внутри — HTTP-сервер
  на 127.0.0.1:8181 (Node http, без внешних модулей): API (D8) + раздача dist/.
  Окно BrowserWindow грузит тот же URL. Портативная сборка — `npm.cmd run app:build`
  → `build/exe/1C Cabinet <версия>.exe` (self-extract, ~105 МБ) + win-unpacked (папка).
- **Почему так:** браузерная версия не могла открыть диалог выбора пути с реальным
  путем (браузеры умышленно скрывают пути — политика приватности); PS-сервер не мог
  гарантированно поднять диалог поверх окон (фоновый процесс без прав foreground,
  перепробованы AllowSetForegroundWindow/SwitchToThisWindow/сторож — см. историю).
  Electron: диалог из main-процесса (`dialog.showOpenDialog`) возвращает реальные
  пути и открывается поверх; коллеге нужен только exe (Chromium и Node зашиты внутрь).
- **Правила запуска из терминалов VS Code:** сбрасывать `ELECTRON_RUN_AS_NODE` (VS Code
  прокидывает ее, и Electron стартует как голый Node). В собранном exe проблемы нет.
- Ядро шагов деплоя по-прежнему PowerShell (runner.ps1, этап 0) — exe будет запускать
  его дочерним процессом, PS-код без изменений.
- **Устарело (оставлено как запасной вариант):** backend/server.ps1 (+ browse-dialog,
  dialog-watchdog) и start-cabinet.cmd — работали, но диалог выбора пути у PS-версии
  не поднимался наверх. Не развивать.
- Рантайм: обычное окно процесса пользователя; автозапуск — ярлык/планировщик от пользователя.

### D11. Портативность (2026-10-30)
- **Текущий формат:** портативная папка `build/exe/win-unpacked/` (запуск `1C Cabinet.exe`)
  или одиночный self-extract `build/exe/1C Cabinet <версия>.exe` (~105 МБ, распаковывается
  при старте). Внутри exe — Chromium, Node-рантайм и наш API; коллеге копировать папку /
  переслать exe — ничего устанавливать не нужно.
- Node.js нужен только на dev-машине для пересборки (electron, electron-builder —
  dev-зависимости в node_modules, без системных установок и прав администратора).
- Кабинет слушает 127.0.0.1 — работает только на машине запуска; доступ коллеги
  со своей машины — отдельное решение (LAN-бинд + брандмауэр, п.8).
- Папки сборки (`build/`, `release/`, `dist/`, `node_modules/`) исключены из .gitignore
  и из файлового вотчера VS Code (.vscode/settings.json) — иначе VS Code держит хэндлы
  на файлах Electron и ломает electron-builder (EBUSY).

### D12. Дескриптор подключения ИБ + «Создать проект для существующей ИБ» (2026-11-02)
- Цель (план пользователя): команда «Создать проект для существующей ИБ» — база уже
  развернута локально (любой путь, например `C:\1C_Bases\InfoBase7`) или на сервере
  (`Srvr="localhost" Ref="infobase1"`). Этап 3 дорожной карты, п.7.
- **Ключевое понятие — дескриптор подключения ИБ**, единый для всех шагов ядра, runner
  и конфигов проекта (вместо «пути к базе»):
  - `kind: file` → `path`;
  - `kind: server` → `srvr`, `ref`, `dbms`, `dbUser`, `dbPassword`.
  Каждый шаг получает дескриптор и сам выводит аргументы: `ibcmd --db-path=` (file) или
  `--server= --infobase= --dbms= --db-user= --db-pwd=` (server); `.dev.env` —
  `INFOBASE_PATH/INFOBASE_KIND` либо серверные поля; .vrd — `File=` либо `Srvr=/Ref=`.
  Структура проекта (build/ib, src/cf, src/cfe) — конвенция/дефолт, НЕ требование:
  конфиги (env.json, .dev.env, bsl-analyzer.toml, vrd) всегда генерируются из дескриптора.
- **Состав пайплайна для существующей ИБ** (визард-режим «подключить проект»):
  пропуск шагов создания ИБ и загрузки .dt; сохраняются: проверка блокировок (для
  server — через сеансы кластера), дампы cf/cfe (главная цель — исходники для AI),
  публикация (Srvr/Ref в .vrd), правила AI, MCP, BSL Analyzer.
- **Проверка блокировок серверной ИБ — права и ПО (уточнение 2026-11-02):**
  на сервер ничего не устанавливается; rac.exe/COMConnector/Конфигуратор — часть
  локальной платформы, администрирование кластера идет удаленно по сетевым портам
  (1545 + диапазоны процессов; должны быть открыты администратором сервера).
  Две стратегии, задаются в настройках проекта:
  - `cluster-admin`: учетка администратора кластера (если задана) — просмотр и
    принудительное завершение сеансов через rac/COM;
  - `ib-blocking`: только право «Администрирование» пользователя ИБ — блокировка
    начала сеансов средствами ИБ + ожидание завершения существующих (принудительное
    завершение чужих сеансов недоступно — для нашей цели «получить исходники»
    достаточно).
  Фолбэк при незарегистрированном COMConnector: пакетный Конфигуратор (/IBConnectionString)
  и rac.
- **Уточнение серверного режима (2026-11-02):** никаких блокировок, завершений
  сеансов и публикаций для серверных ИБ — публикацию делает администратор сервера.
  Занятость базы — только мягкое предупреждение (попытка подключения; занято →
  сообщить и ждать/отменить, принудительных действий нет).
  Состав шагов серверного режима: установка расширения MCP (по выбору), дампы cf/cfe,
  правила AI, конфиг MCP-инструментов в проекте. Пропуск: создание ИБ, .dt, блокировки,
  публикация.
  Данные, необходимые для MCP поверх чужой публикации:
  - URL публикации базы (MCP-эндпоинт = `<URL>/hs/mcp-1c`);
  - в default.vrd публикации HTTP-сервисы должны публиковаться:
    httpServices publishByDefault="true" и publishExtensionsByDefault="true"
    (иначе попросить администратора сервера включить — это на его стороне);
  - учетка ИБ с полными правами (агент авторизуется сам);
  - установка расширения MCP — в базу через Конфигуратор/ibcmd, перезапуск
    на сервере не требуется (исключение: профили безопасности кластера, если
    настроены — редкость).
- **Обязательство к этапу 0:** функции Modules/Core принимают дескриптор подключения
  (не путь), чтобы режим «существующая ИБ» лег без переписывания ядра. В манифесте
  деплой-визарда — поле `ib: { kind, path | srvr/ref/dbms/dbUser }`.
- Реализация — этап 3 дорожной карты; сигнатуры функций этапа 0 проектируются с учетом
  настоящего решения.

### D14. Детальная карточка проекта: инфо из выгрузки исходников + обновление + команды открытия (2026-11-03)
- **Источник данных — выгрузка исходников проекта**, ИБ на время чтения не нужна:
  - `src/cf/Configuration.xml` (читается «голова» файла, 256 КБ — Properties в начале):
    Name, Synonym (первый v8:content), Version (точный релиз), Vendor,
    ConfigurationExtensionCompatibilityMode;
  - `src/cfe/<Имя>/Configuration.xml` — расширения: имя, синоним, версия,
    `ConfigurationExtensionPurpose` (AddOn/patch/Customization). Расширения с
    назначением **Patch объединяются одной строкой «Патчи: …»**, остальные
    показываются построчно («Расширение: имя — добавление (версия)»);
  - `.dev.env` — INFOBASE_KIND (file|server), INFOBASE_PATH (или INFOBASE_SRVR/
    INFOBASE_REF для server — формат задел под D12/этап 3), IB_USER,
    PLATFORM_VERSION/PLATFORM_PATH, INFOBASE_PUBLISH_URL.
- **Хранение:** разобранная информация — в записи проекта реестра (`registry.json`):
  поля `info` (объект ProjectInfo) и `infoUpdatedAt` (ISO-дата последнего обновления).
  GET /api/projects отдает их вместе с записью.
- **Обновление — `POST /api/projects/info { projectDir }`**, транзакционно: сначала
  вся информация собирается в память; при любой ошибке реестр не изменяется и
  возвращается `500 { error: "Не удалось обновить данные по проекту по причине: <текст>" }`
  (фронт показывает тост, старые данные остаются). При успехе пишутся `info` +
  `infoUpdatedAt`. Ограничение: обновление читает **текущую выгрузку** — если
  конфигурация менялась в ИБ без последующего дампа cf/cfe, данные будут по
  последнему дампу (переснятие дампов из ИБ — отдельная будущая команда).
- **Команды открытия — `POST /api/projects/open { projectDir, target }`**:
  - `vscode` — Code.exe из настроек кабинета (tools.vscode) или автопоиск;
  - `designer` / `enterprise` — `1cv8.exe DESIGNER|ENTERPRISE`; платформа:
    `PLATFORM_PATH\bin\1cv8.exe` из .dev.env → настройки кабинета → автопоиск;
    подключение: файловая `/F"путь"`, серверная `/S"сервер\база"`; пользователь
    `/N"IB_USER"` и пароль `/P"IB_PASSWORD"` (если заданы) — из .dev.env проекта;
    запуск отдельным процессом (detached, окна не скрываются).
- UI: карточка проекта — блок деталей (конфигурация/релиз/поставщик, платформа,
  база, расширения, патчи, «Обновлено: дата время») + кнопки «Обновить
  информацию», «Открыть в VS Code», «Открыть конфигуратор», «Открыть
  Предприятие» и удаление. Пока info не собрано — плашка с приглашением нажать
  «Обновить информацию».

### D13. Шаблоны конфигураций: реестр + источник мастера (2026-11-03, план; реализовано 2026-11-09)
- Цель: разворачивание базы из **установленного шаблона типовой конфигурации**
  (сценарий: releases.1c.ru → скачивание zip → setup.exe →
  `C:\1C_Bases\SHABLONI\Разработчик\Имя\Версия`).
- **Реестр шаблонов (реализовано):** сканирование каталога шаблонов (настройка
  «Каталог шаблонов конфигураций», `tools.templatesRoot`, дефолт
  `C:\1C_Bases\SHABLONI`, автопоиск в main.cjs) на 3 уровня
  `<Разработчик>\<Имя>\<Версия>`. Шаблон = каталог с `1Cv8.cf` или хотя бы одним
  `*.dt`. `GET /api/templates` возвращает `{ root, templates[] }`, каждый шаблон:
  `{ vendor, name, version, dir, cfPath, mft, sources[] }`.
- **Разбор `1cv8.mft`:** Vendor/Name/Version/AppVersion + секции [ConfigN]
  (Catalog/Destination/Source). Источник считается **демо**, если Catalog
  содержит «демо» (покрывает и «демонстрационная база», и «(демо)»); источники
  из mft фильтруются по фактическому наличию файла в каталоге версии. Без mft —
  все `*.dt` помечаются демо.
- **Создание ИБ из шаблона (реализовано):** в мастере — переключатель
  «Источник информационной базы»: «Файл выгрузки .dt» (как раньше) |
  «Шаблон конфигурации» (список из GET /api/templates + выбор источника в
  шаблоне). **Источник по умолчанию — выгрузка с демо-данными** (замечание
  пользователя 2026-11-09: база из cf пустая, без данных для тестирования;
  дефолт = демо-`*.dt`, иначе любая `*.dt`; «только конфигурация (1Cv8.cf)» —
  осознанный выбор полностью пустой базы, дефолтом не бывает). Два случая:
  - выбрана выгрузка `*.dt` из шаблона (новая база/демо) → обычный путь
    `ibcmd create --restore` (в манифесте — dtPath на файл шаблона);
  - выбрана «только конфигурация (1Cv8.cf)» → новая функция ядра
    `New-CoreInfobaseFromCf` (Core.Infobase): одна команда
    `ibcmd infobase create --create-database --load=<cf> --apply --force`
    (проверено на реальном шаблоне BuhSh 873 МБ; **--force обязателен** — без
    него ibcmd на реструктуризации хранилища расширений задает интерактивный
    вопрос «Принять изменения [y/n]» и отменяет обновление, код выхода 102).
  В манифесте деплоя — поля `dtPath` (взаимоисключаемо) и `templateCfPath`
  (+ `ibSource` для читаемости); валидация /api/deploy требует ровно один
  источник и существование файла. Идемпотентность шага 04 сохранена (пропуск,
  если каталог ИБ непуст). Дальше — общий конвейер (дампы, MCP, правила,
  публикация) без изменений.
- **Установка шаблона из скачанного zip (реализовано, частично):**
  `POST /api/templates/install { zipPath }`: Expand-Archive (powershell) во
  временную папку → поиск файлов шаблона (`1cv8.mft` или `1Cv8.cf`) в корне
  архива или до 3 уровней ниже → копирование в дерево каталога шаблонов;
  имена каталогов — из mft (Vendor/Name/Version, недопустимые в путях символы
  → `_`), фолбэк — имена папок архива. Если в архиве только `setup.exe` без
  файлов шаблона — установка не выполняется: возвращается 400 с объяснением
  (тихий ключ не определен; файлы нужно установить вручную). Скачивание с
  releases.1c.ru **не автоматизируем** (авторизация + условия использования) —
  ручной шаг пользователя. Кнопка «Установить из zip…» — в мастере рядом со
  списком шаблонов.
- **Не реализовано (ждет дистрибутива):** неинтерактивная установка шаблона
  через setup.exe — ключ тихого режима определяется эмпирически на первом
  реальном дистрибутиве; до тех пор архивы «только setup.exe» обрабатываются
  понятной ошибкой.
- Реализация — **после успешной регрессии этапа 0 на реальной .dt** (выполнено:
  регрессия 2026-11-03, деплой ka_demo 2026-11-06).

### D3. Frontend: **TypeScript SPA — да, JavaScript/TypeScript использовать можно и рекомендуется**

### D4. Разделение на слои (главный принцип модульности)
GUI только показывает и запускает; вся логика — в переиспользуемом ядре:

```

  ↕ REST + SSE
```

### D5. Рефакторинг монолита в ядро-модуль
Требования к каждому шагу:
- **Никакого Read-Host / Ask-YesNo** — параметры приходят объектом-манифестом (JSON); интерактив заменен валидацией с кодами ошибок (решение принимает UI).
- Структурированный результат: `{ step, status, durationSec, logPath, error }`.
- События прогресса — **JSON-lines** (`steps.jsonl`): `{ ts, step, phase, detail, elapsed }`; «Обрабатывается: X» из лога дизайнера попадает в `detail`.
- Идемпотентность и маркерные блоки — сохранить как есть.

### D6. Job Runner — модель прогонов
- Каждый деплой = **отдельный процесс** `powershell.exe -File runner.ps1 -RunManifest <json> -RunDir <dir>`.
- UI/сервер могут перезапуститься — прогон продолжится, статус дочитывается из файлов (`runs/<id>/state.json` + `steps.jsonl` + логи ibcmd, которые и сейчас пишутся в `build\*.log`).
- Параллельные прогоны разрешены, но: **один Apache / один порт** и **одна ИБ = одна ibcmd-операция** — очередь/файловые lock-файлы на уровне реестра.

### D7. Реестр проектов и данные
- `C:\1C_Bases\AI\registry.json` — центральный индекс; в каждом проекте `project.json`.
- `project.json` (черновик схемы): `name, path, kind: "file"|"server" (заложено сразу), ibPath, platformPath, platformVersion, dbUser, publish { url, webClientUrl, mcpUrl, vdir, port, apacheDir }, mcpServers[], createdAt, lastDeployAt, status, runs[]`.
- История: `runs/<runId>/manifest.json`, `steps.jsonl`, логи stdout/stderr.
- **Секреты** (пароль ИБ): DPAPI (`ConvertFrom/To-SecureString` текущего пользователя), в открытом виде не хранить.

## 8. Риски и тонкости (учесть)

- PS 5.1: `ConvertTo-Json -Depth`, UTF-8 **no BOM**, экранирование аргументов `Start-Process` (массивы склеиваются без кавычек!), `2>&1` при `$ErrorActionPreference=Stop` — в текущем скрипте это уже решено, переносить как есть.

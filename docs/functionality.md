> **Назначение файла:** принцип работы того, что уже сделано («как сейчас»).
> «Как будет» — в docs/decisions.md. Правила ведения — в AGENTS.md, п.3.

Статус на 2026-10-30: фронтенд (Vite + TypeScript): вход, рабочий стол
с вкладками, настройки с проверкой путей через бэкенд, мастер новой

на TcpListener, без внешних модулей (decisions.md, D2/D8). Полный рефакторинг

## Вход и пользователи (users.json через бэкенд)

- Профили хранит **бэкенд**: `%LOCALAPPDATA%\1c-deploy-cabinet\users.json`
  (массив `{ name, createdAt, lastLoginAt }`). Файл общий для всех адресов
  и портов — профиль не «теряется» при переходе с localhost:5173 на 127.0.0.1:8180
  (до 2026-10-30 профили жили в localStorage и были привязаны к адресу сайта).
- Экран входа (`src/pages/login.ts`): подсказка при вводе — `GET /api/users?prefix=`
  с точным сравнением имени (дебаунс 250 мс); вход — `POST /api/login { name }`
  (бэкенд создает или обновляет lastLoginAt, отвечает `{ isNew }`).
  «Последний пользователь» для автологина — `cabinet_lastUser` в localStorage
  (метка сессии конкретного браузера, намеренно).
- Фолбэк при недоступном бэкенде: localStorage (`cabinet_users`,
  `src/lib/storage.ts` — `loadUsers/findUser/upsertUserLogin` сохранены) +
  тост-предупреждение. Устаревшие профили из localStorage автоматически
  не переносятся — при первом входе профиль создается в users.json.

## Глаша (внешний сервис)

- Кнопка «Перейти в Глашу» (вкладка «Глаша») открывает `http://glasha.fortlab.local/`
  (константа `GLASHA_URL` в `src/pages/desktop.ts`).
- В Electron-приложении внешний сайт открывается **в том же окне**:
  main-процесс перехватывает навигацию вне APP_ORIGIN (`will-navigate`),
  грузит внешний сайт и внедряет фиксированную кнопку **«← Вернуться в
  личный кабинет»** (правый верхний угол; внедрение повторяется на каждый
  `did-finish-load`, пока включен режим externalMode). Кнопка ведет на
  `APP_ORIGIN/#/desktop` — рабочий стол кабинета. Popup'ы и target=_blank
  внешнего сайта уходят в системный браузер (`setWindowOpenHandler`).
- В браузерной дев-версии (Vite 5173) внешняя ссылка открывается в браузере
  штатно (назад — кнопка браузера).

## Запуск и сборка (Electron, с 2026-10-30)

- **Готовое приложение:** `build/app/1C Cabinet <версия>.exe` (self-extract, ~105 МБ)
  или портативная папка `build/app/win-unpacked/` (запуск `1C Cabinet.exe`).
  Внутри exe — Chromium, Node-рантайм, runner и API; снаружи ничего устанавливать
  не нужно. ВАЖНО: каталог `build/exe/` может остаться «залоченным» Windows
  (антивирус/проводник держат хэндлы на файлах Electron) — вывод сборки перенесен
  в `build/app/`; залоченные старые папки удаляются только после перезагрузки.
  Запускать сборку при работающем кабинете из win-unpacked нельзя (EBUSY).
- Окно кабинета — Electron BrowserWindow, грузит встроенный сервер
  http://127.0.0.1:8181 (main-процесс `electron/main.cjs`: тот же API, что был
  в server.ps1 — см. D8, плюс раздача dist/). Запускается **развернутым**
  (maximize); **F11** — переключение настоящего полного экрана.
- Диалог 📁 в настройках — нативный `dialog.showOpenDialog` из main-процесса:
  возвращает реальные пути и открывается поверх окон.
- Повторный запуск exe при уже работающем кабинете: второй экземпляр завершается,
  первый показывает свое окно (single-instance lock).
- **Медленный старт self-extract exe (~5–10 с)** — это распаковка во временную
  папку при каждом запуске. Быстрая альтернатива — ярлык на
  `build/exe/win-unpacked/1C Cabinet.exe` (та же программа, старт мгновенный;
  для коллеги копировать всю папку win-unpacked, например переименовав в «1C Кабинет»).
- Разработка: `npm.cmd run dev` (Vite 5173, /api проксируется на 8181 — нужен
  запущенный exe или `npm.cmd run app`); `npm.cmd run app` — Electron из исходников;
  `npm.cmd run app:build` — сборка фронта + портативного exe (electron-builder).
- **Нюансы:** из терминалов VS Code сбрасывать `ELECTRON_RUN_AS_NODE` перед запуском
  electron; папки build/, release/, dist/, node_modules/, files/ исключены из .gitignore
  и из вотчера/поиска VS Code (.vscode/settings.json) — иначе VS Code держит хэндлы
  на файлах Electron и electron-builder падает (EBUSY). Папка build/ видна в
  проводнике VS Code намеренно.
- **Иконка:** исходник `public/icon.png` (1024×1024, копия из files/icon.png).
  electron-builder конвертирует ее в ico для exe (`build.win.icon`); то же
  изображение — иконка окна/панели задач (ICON_PATH в main.cjs) и favicon
  страницы (index.html). После пересборки Проводник может показать старую
  иконку из кэша — обновление (F5) или переименование файла помогает.
- **Устарело:** `backend/server.ps1` + start-cabinet.cmd (PS-версия, диалог не
  поднимался наверх) — оставлены как запасные, не развивать.

## Карточки проектов: детали, обновление информации, открытие (2026-11-03)

- **Данные карточки** собираются бэкендом из выгрузки исходников (D14, decisions.md):
  `src/cf/Configuration.xml` (конфигурация, точный релиз, поставщик, режим
  совместимости), `src/cfe/*/Configuration.xml` (расширения: имя, версия,
  назначение; патчи (Patch) объединяются одной строкой «Патчи: …»), `.dev.env`
  (тип ИБ файловая/серверная, путь/адрес, пользователь, платформа, публикация).
- **Хранение:** в записи проекта `C:\1C_Bases\AI\registry.json` — поля `info`
  и `infoUpdatedAt` (дата/время последнего обновления, показывается в карточке).
  GET /api/projects отдает их вместе с проектом.
- **Обновление:** кнопка «Обновить информацию» в карточке →
  `POST /api/projects/info { projectDir }`. Транзакционно: ошибка → реестр не
  меняется, тост «Не удалось обновить данные по проекту по причине: …» (текст
  причины приходит от бэкенда), старые данные остаются; успех → запись info +
  infoUpdatedAt, карточка перезагружается. Ограничение: читается текущая
  выгрузка — изменения в ИБ без последующего дампа cf/cfe не видны.
- **Открытие:** кнопки «Открыть в VS Code» / «Открыть конфигуратор» /
  «Открыть Предприятие» → `POST /api/projects/open { projectDir, target }`.
  VS Code — Code.exe из настроек кабинета (или автопоиск), с флагом **`-r`**:
  если редактор уже запущен, проект открывается в последнем активном окне
  вместо нового окна. Конфигуратор — `1cv8.exe DESIGNER` (через ЛАУНЧЕР:
  толстый клиент `1cv8c.exe` ключ DESIGNER не распознает и молча открывает
  Предприятие); Предприятие — толстый клиент `1cv8c.exe` НАПРЯМУЮ из 64-битной
  установки (`C:\Program Files\1cv8\<версия>\bin\1cv8c.exe`), т.к. лаунчер сам
  подменяет клиента на per-user x86 (%LOCALAPPDATA%\Programs\1cv8_x86);
  фолбэк — PLATFORM_PATH из .dev.env, затем настройки кабинета; разрядность
  показывается в тосте только для прямого запуска 1cv8c.exe; подключение и
  ключ передаются
  **отдельными аргументами** (`/F <путь>`, `/S <сервер\база>`, `/N <польз>`,
  `/P <пароль>` — из .dev.env проекта); склеенный токен `/F"путь"` Node
  экранирует кавычками и 1cv8 его не распознает (выглядело как попытка открыть
  `C:\1Cv8.1CD`). Ошибки (нет Code.exe, нет каталога ИБ, серверные поля не
  заданы) приходят тостом. У кнопок — иконки: VS Code (inline-SVG,
  константа VSCODE_SVG), конфигуратор/предприятие — `src/assets/designer.png`
  и `src/assets/enterprise.png` (копии из files/, подмена = заменить файл).
- **Проверка публикации в карточке** (2026-11-06): рядом с «Публикация: …» —
  точка статуса (серая «проверяется…» → зеленая «доступна» / красная
  «недоступна»). Бэкенд: `POST /api/projects/check-publish { publishUrl }` —
  один локальный HTTP GET на URL публикации (таймаут 4 с; 2xx–4xx = доступна,
  5xx/обрыв/таймаут = нет). Ресурсоемкость — миллисекунды на проект, проверка
  запускается при отрисовке карточек. Проверка честно выявляет и «битые»
  публикации (например, у bpsx 06.11.2026 оказался удален файл ИБ
  `build\ib\1Cv8.1CD` — Apache отдает 500, точка красная).
- **Удаление проекта — окно ожидания:** после подтверждения содержимое модала
  заменяется вращающимся кружком (CSS-анимация .modal-spinner) и текстом
  «Удаление проекта…»; по завершении — тост и обновление списка.
- **Runner: httpd запускается с WorkingDirectory = каталог bin Apache**
  (Core.Publish.psm1): иначе httpd наследует рабочий каталог кабинета
  (win-unpacked) и блокирует пересборку exe (EBUSY — случилось 06.11.2026
  после деплоя ka_demo).
- **Apache portable при старте кабинета** (2026-11-05): при запуске приложения
  бэкенд проверяет порт `Listen` из `conf\httpd.conf` (TCP-проба 127.0.0.1);
  если никто не слушает — запускает `httpd.exe` скрытым процессом. Путь Apache
  — из настроек кабинета (tools.apache) либо дефолт
  `C:\1C_Bases\AI\tools\apache_portable\Apache24\bin\httpd.exe`; лог — в
  консоль процесса (ensureApacheRunning в `electron/main.cjs`).
- Файлы: `electron/main.cjs` (collectProjectInfo, parseDevEnvMap,
  parseMetadataHead, handleProjectsInfo, handleProjectsOpen), `src/pages/desktop.ts`
  (projectCard + projectInfoBlock), `src/styles/projects.css` (project-info*,
  project-actions, project-btn), типы `ProjectInfo/ProjectExtensionInfo` в
  `src/api/client.ts`.
- **Макет карточки** (по замечаниям 2026-11-03): наименование проекта крупно
  (18px), под ним — конфигурация (синоним, 15px, полужирно), строкой ниже —
  «Релиз X»; дальше «База: Файловая|Серверная» (без пути/пользователя),
  платформа, затем путь проекта и публикация; блок «Расширения:» — построчно
  имя (версия), без указания типа; патчи — одной строкой «Патчи: …»; поставщик
  не показывается; в конце «Обновлено: дата время».

## Мастер новой развертки (маршрут #/new-project)

- Открывается кнопкой «Запустить помощник развертки» на вкладке
  «Добавить новый проект» (src/pages/newProject.ts, стили wizard.css).
- 4 шага без перегруза формы: 1) Проект (имя, папка, шаблон — необяз., .dt);
  2) Платформа (список из GET /api/platforms; по умолчанию выбрана самая свежая,
  кнопка «Следующий шаг» активируется автоматически);
  3) Доступ и публикация: флаг «Информационная база без пользователей» (выключен
  по умолчанию; при включении логин и пароль очищаются, поля гасятся и становятся
  необязательными),
  выбор логина\пароля из списка типовых баз (`IB_PRESETS` — УТ, БП, ЗУП,
  Розница 3.0/УНФ, Розница 2.3 — подставляет логин и пароль, показывает
  типовую базу) или произвольный ввод (нужен пользователь с полными правами),
  пароль (не сохраняется на диск, DPAPI — этап 0), префикс ФК_, порт 8080,
  каталог Apache (проводник, дефолт из настроек);
  4) Компоненты — все флажки включены по умолчанию (правила ai_rules_1c /
  BSL Analyzer / справочник платформы) + предпросмотр манифеста.
- **Автозаполнение из настроек:** мастер строится только после загрузки
  настроек (плашка «Загрузка настроек…»), поэтому дефолты гарантированно
  в полях: папка проекта ← «Корневой каталог проектов», шаблон ← «Шаблон
  проекта», каталог Apache ← из пути httpd.exe.
- **Кнопки проводника** (иконка папки) у «Папка проекта» (выбор каталога),
  «Шаблон проекта» (каталог) и «Файл выгрузки .dt» (файл с фильтром .dt) —
  POST /api/tools/browse с параметрами { kind, filter, defaultPath }:
  диалог открывается в каталоге текущего значения поля.
- Кнопки «← Предыдущий шаг» и «Следующий шаг →»; «Следующий шаг» неактивна,
  пока есть незаполненные обязательные поля шага (ошибки подсвечиваются под
  полями). Крестик «×» в шапке закрывает помощник и возвращает на рабочий
  стол (введенные данные не сохраняются). На последнем шаге кнопка —
  «Развернуть»: POST /api/deploy, ошибки
  бэкенда (нет .dt, плохой порт и т.п.) показываются списком; успех —
  экран с runId и путем манифеста.

## Шаблоны конфигураций (D13, 2026-11-09)

- **Реестр шаблонов** — `GET /api/templates`: сканирование каталога шаблонов
  (настройка «Каталог шаблонов конфигураций», `tools.templatesRoot`, автопоиск
  — дефолт `C:\1C_Bases\SHABLONI`) на 3 уровня `<Разработчик>\<Имя>\<Версия>`.
  Шаблон = каталог с `1Cv8.cf` или `*.dt`. Разбирается `1cv8.mft` (Vendor/Name/
  Version + секции [ConfigN]: Catalog/Source); источник помечается демо, если в
  Catalog есть «демо». Ответ: `{ root, templates: [{ vendor, name, version,
  dir, cfPath, mft, sources: [{ file, demo, label }] }] }`.
  Файлы: `electron/main.cjs` (parseMft, scanTemplates, handleTemplates).
- **Мастер развертки, шаг 1** (src/pages/newProject.ts, renderStepProject +
  renderTemplatePick): переключатель «Источник информационной базы» —
  «Файл выгрузки .dt» (поле как раньше) | «Шаблон конфигурации» (список
  шаблонов с наличием cf/выгрузок, выбор источника в шаблоне: по умолчанию —
  выгрузка с демо-данными (данные для тестирования), иначе первая .dt;
  «только конфигурация (1Cv8.cf)» — пустая база, дефолтом не бывает;
  кнопки «Обновить список», «Установить из zip…»). В манифест уходит
  ровно один источник: `dtPath` (файл или выгрузка из шаблона) или
  `templateCfPath` (1Cv8.cf).
- **Создание ИБ из шаблона:** шаг 04 runner ветвится (runner.ps1): есть dtPath
  → `New-CoreInfobaseFromDt` (как раньше); иначе `templateCfPath` →
  `New-CoreInfobaseFromCf` (runner/Modules/Core.Infobase.psm1): одна команда
  `ibcmd infobase create --create-database --load=<cf> --apply --force`.
  `--force` обязателен: без него ibcmd на реструктуризации хранилища расширений
  спрашивает «Принять изменения [y/n]» и отменяет обновление (код 102).
  Идемпотентность как у dt-варианта (непустой каталог ИБ → пропуск).
  Валидация манифеста: ровно один источник, файл существует.
- **Установка шаблона из zip** — `POST /api/templates/install { zipPath }`:
  Expand-Archive во временную папку → поиск `1cv8.mft`/`1Cv8.cf` в корне архива
  или до 3 уровней ниже → копирование в дерево каталога шаблонов; имена
  каталогов из mft (Vendor/Name/Version; `\/:*?"<>|` → `_`), фолбэк — имена
  папок архива. Архив «только setup.exe» (установщик 1С без файлов шаблона) —
  400 с понятной ошибкой: тихий ключ установки не определен (ждет реального
  дистрибутива с releases.1c.ru, скачанного вручную). Файлы: main.cjs
  (handleTemplatesInstall, findTemplateRoots, copyDirContents, sanitizeName).

## Настройки (пути к обязательному ПО)

- Два входа: шестеренка на экране входа (правый верхний угол,
  `src/pages/login.ts`) и шестеренка в topbar рабочего стола
  (`src/components/topbar.ts`) → маршрут `#/settings`,
  страница `src/pages/settings.ts`, стили `src/styles/settings.css`.
- Каталог ПО — `TOOL_CATALOG` в `src/lib/settings.ts`, четыре раздела:
  «Каталоги развертки» (корневой каталог проектов, шаблон проекта, каталог
  шаблонов конфигураций — используются мастером развертки), «Инструменты
  разработчика» (VS Code, Git — необязателен, только для правил ai_rules_1c),
  «Платформа 1С» (1cv8.exe, ibcmd.exe),
  «Публикация и AI-инструменты» (Apache, Java 17+, BSL Analyzer).
  Node.js/npm в каталог не входит — инструмент сборки кабинета, деплою не нужен.
  У каждой позиции `kind`: file (проверка/выбор файла) или dir (каталог).
- Точка статуса проверяет путь **бэкендом** (debounce 350 мс): зеленая — файл
  найден, красная — не найден/не задан, серая — «проверяется…» (или бэкенд
  недоступен — тогда зеленая с пометкой «проверка позже»).
- Кнопки у каждой позиции: 📁 — проводник (нативный `dialog.showOpenDialog`
  Electron-приложения, для каталогов включено создание новой папки),
  «Автопоиск» — POST /api/tools/detect (PATH, стандартные каталоги; где
  ищет — в tooltip), «×» — очистить. Все запросы API имеют таймаут (30 с,

- Правки — в черновике страницы, применяются кнопкой **«Сохранить настройки»**:
  сохранение (PUT /api/settings → settings.json) + автоматический выход на

- Хранение: файл `%LOCALAPPDATA%\1c-deploy-cabinet\settings.json` через бэкенд;
  при недоступном бэкенде — localStorage (`cabinet_settings`,

## Runner развертки (этап 0, часть 1)

- `runner/runner.ps1` + `runner/Modules/Core-*.psm1` — исполнитель пайплайна
  деплоя (перенос deploy-new-1c-project-ru-publish.ps1). Все файлы PS 5.1,
  UTF-8 **с BOM** (кириллица ломается без BOM).
- Запуск: `powershell -NoProfile -ExecutionPolicy Bypass -File runner\runner.ps1
  -Manifest <путь к manifest.json>`. Манифест — JSON с полями манифеста деплоя
  (runId, runDir, projectDir, templateDir, dtPath, dbUser, prefix, apacheDir,
  publishPort, noUsers и т.д.); отсутствующие поля замещаются дефолтами скрипта.
- События шагов: `{ ts, step, phase: start|progress|success|error|skipped,
  detail }` → `<runDir>/steps.jsonl` (пишет приемник Set-StepEventSink из
  Core.Common). Прогресс длинных операций — «Обрабатывается: X (мм:сс)»
  из хвоста stdout процесса. Итог: `<runDir>/state.json` (status/error/steps).
- Часть 1 — шаги: 00 валидация, 01 платформа+ibcmd (автодетект или из
  манифеста), 02 проект (эталон + структура, флаг allowNonEmptyProjectDir),
  03 .dev.env/env.json (файловая ИБ; серверная форма — часть 2), 04 ИБ из .dt
  (реальный ibcmd, идемпотентно), 05 блокировки (поллинг locksWaitSec вместо
  интерактива), 06 установка MCP_HTTPService (mcp-1c -install + safe-mode off,
  идемпотентно), 07 дамп cf, 08 дамп cfe, 09 публикация Apache (перенос 1:1),
  10 правила ai_rules_1c (git-кэш + install.ps1 init, фолбэк на локальную копию),
  11 bsl-analyzer (install.ps1 → toml + kilo.json + USER-RULES), 12
  mcp-bsl-platform-context (java 17+, jar с GitHub Releases → kilo.json +
  USER-RULES), 13 MCP-конфиг (1c-data-mcp → stdio-прокси, докер-серверы каталога
  отключены). Дымовые тесты: пайплайн до реального ibcmd включительно и
  kilo.json-функции — пройдены (2026-11-02).
- Дымовой тест 2026-11-02: реальный ibcmd создал ИБ, невалидный .dt дал
  чистую ошибку шага 04, events/state корректны (exit 1).
- **Интеграция с exe (часть 3):** «Развернуть» в мастере → POST /api/deploy →
  приложение запускает runner.ps1 скрытым дочерним процессом (манифест прогона)
  и отвечает runId; мастер переключается на **монитор прогона**: список всех
  шагов runner со статусами и живым прогрессом, опрос
  `GET /api/deploy/status?runId=` раз в 1.5 с (state.json + steps.jsonl).
  Ошибка/успех завершают монитор итоговой плашкой. Консольный вывод runner —
  в `<runDir>/runner-console.log` (диагностика запуска). Шаги идемпотентны:
  повторный прогон по существующему проекту пропускает выполненное (дампы, ИБ);
  параллельные прогоны одного runId не защищены — защита в планах.
- **Ловушка spawn (2026-11-03):** spawn powershell из Electron с флагами
  `detached: true` + `windowsHide: true` вместе — процесс молча умирает, не
  выполнив скрипт. Используется только windowsHide (без detached) + stdio в
  файл `<runDir>/runner-console.log`.
